## 业务规则（可断言）

- **R1** 报告的「结构是否正常」结论，只在**后端** `FormatReport` 计算一次，前端不得自行判断。
  （用户 2026-10-23 拍板）
- **R2** `chapterCount == 0 && bodyParagraphs == 0` 时，报告必须标记为 `EMPTY`，文案为「未检测到任何正文内容」。
  （用户拍板：区分空文档与正常文档）
- **R3** `chapterCount == 0 && bodyParagraphs > 0` 时，报告必须标记为 `WARN`，文案指出「未识别到章节标题」并给出两种常见原因。
  （由 R2 反推：有正文但没标题是另一种异常）
- **R4** 仅当 `chapterCount > 0` 且 `suspects` 为空时，界面才允许显示「结构识别良好」。
  （R2/R3 的补集）
- **R5** 批量提交时，单个文件上传失败不得中断其余文件；所有上传成功的文件必须建成排版任务。
  （用户拍板：成功照常提交）
- **R6** 批次结束后必须汇总：成功 N 篇 / 失败 M 篇（含文件名与原因），失败文件保留在待提交区，成功文件移出。
  （用户拍板：汇总提示）
- **R7** `upload` 收到的文件前 4 字节必须是 `PK\x03\x04`，否则以业务错误拒绝，且**不落存储、不入库**。
  （用户拍板：仅后端校验）
- **R8** 用户可见的失败文案不得出现重复前缀（如「排版失败：排版失败：」），不得出现异常类名、十六进制签名等技术细节。
  （代码事实：现状违反）
- **R9** 本次不改排版引擎的格式逻辑，不改模板配置，不动存量历史数据。

## 反直觉细节（记录下来，避免后续误判）

1. **空文档排版是「成功」的**：引擎不抛异常，任务状态是 `SUCCESS`、产物是一份空白文档。
   所以不能靠「任务失败」提示用户，必须在报告层判定 —— 这是 R1 必须放后端的原因。
2. **业务错误时 HTTP 状态码是 200**：`Result` 统一包装，真正的错误码在 `body.code`（例如 `{"code":400,"message":"文件不能为空"}`）。
   判断上传是否成功不能看 HTTP 状态，必须看 `body.code`。
3. **0 字节文件的失败发生在 `upload` 阶段**，坏文件（伪 docx）目前要到 `format` 阶段才失败。
   修复后两者都在 `upload` 阶段拒绝，前端不再产生「已入库但无任务」的中间态。
