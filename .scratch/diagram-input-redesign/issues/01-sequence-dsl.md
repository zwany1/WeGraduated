## What to build

让用户打开系统图页、切到时序图时，可以直接敲几行文本出图，而不是逐条加参与者与消息。
这条链路要完整穿过：文本输入 → 后端解析 → 图模型 → 画布渲染 → 保存 → 再次打开文本仍在。

1. 后端新增 DSL 服务，承担两个方向：
   - `parse(type, text)`：文本 → 对应图的 Config；失败时返回**结构化错误**（行号 + 无法识别的片段 + 该图语法提示）
   - `render(type, config)`：Config → 文本（R4 的载体，没有它用户在画布上的改动切回文本就会丢）
2. 实现 **SEQUENCE 方言**：核心记号 `->`（request）/ `-->`（return）/ `: 标签` / `#` 注释；
   参与者由消息两端自动推导，无需单独声明。
3. 支持的 type 只包含 8 种图；TABLE3 传入时明确拒绝并提示走三线表页面（R1 的判定点）。
4. 生成接口接受 DSL 文本；DSL 文本随图持久化，使再次打开能回填输入框。
5. 前端时序图面板：文本输入框（防抖预览）、错误行号提示、一键填入示例。

## 验收标准

1. 给定文本
   ```
   用户 -> 系统: 登录请求
   系统 -> 数据库: 查询账号
   数据库 --> 系统: 返回结果
   系统 --> 用户: 登录成功
   ```
   当以 `SEQUENCE` 解析，那么产出的配置含 3 个参与者（用户 / 系统 / 数据库）与 4 条消息，
   且第 3、4 条的 `type` 为 `return`，消息顺序与文本一致。

2. 给定上述文本但把第 3 行写成 `数据库 >> 系统: 返回结果`，当解析，
   那么失败结果 `line = 3`，且 `snippet` 含 `>>`，并附带该图的语法提示。

3. 给定任意合法 SequenceConfig，当 `render` 后再 `parse`，
   那么参与者数、消息数、以及每条消息的 `from` / `to` / `text` / `type` 全部等价（往返一致）。

4. 给定 `type = TABLE3`，当解析，那么被拒绝且提示指向三线表页面，而不是静默走通用逻辑。

5. 给定一段 DSL 生成图并保存，当再次加载该图，那么回填到输入框的文本与保存前一致。

6. 给定一张**只存了结构化配置、没有 DSL 文本**的老图，当加载，
   那么输入框由 `render` 反向生成填充；若 `render` 也失败，输入框留空但表单照常可用（不得阻断编辑）。

## 约束

- 解析不得调用任何外部服务（R3）；单测中不启 Spring、不连库。
- 不修改 RuleEngine 产出的图模型结构，只在其上新增解析层。
- 示例文本取自真实论文场景，不用 foo/bar。
