# 系统图设计页：文本 DSL 输入改造

> Design 站产出。上游：`.scratch/diagram-input-redesign/state.md`（Brainstorm 规则 R1–R10）。

## 1. Problem Statement

系统图设计页提供 9 种图，其中 8 种（FLOW / ARCH / SWIMLANE / ACTIVITY / USECASE /
SEQUENCE / CLASS / ER）目前只能靠**结构化表单逐项填写**才能出图。嵌套越深的图越难填：
类图要逐条加「类 → 属性 → 方法 → 关系」，时序图要逐条加「参与者 → 消息」，用例图要
先建参与者再建用例再连关系。用户反馈「填字段太繁琐」。

同时存在能力错配：后端 `DiagramGenerator` 本就有「自然语言 → 图」的关键词解析入口，
`GenDTO` 里也预留了 `description` 字段，但 UI 只暴露了结构化表单这条路，文本入口基本没用上。

三线表（TABLE3）不在问题范围内 —— 它是表格而非图，且已有「粘贴建表 SQL 自动解析」的
批量入口，交互满意度没问题。

## 2. Solution

为 8 种图各提供一种**轻量文本 DSL** 作为主输入入口：用户按极简语法写几行大纲式文本，
即可生成图；生成后可在画布上直接编辑（拖节点 / 双击改文案 / 拉连线），原表单折叠保留
作为精确调整的兜底。

解析与反向生成**全部在后端 Service 层**完成，前端不重复实现语法，保证「文本 ↔ 图模型」
两端语义唯一。

### 统一核心记号（8 种图共用）

| 记号 | 含义 |
| --- | --- |
| `A -> B` | 实线 / 顺序流 |
| `A --> B` | 虚线 / 返回 |
| `A --> B: 标签` | 带标签的连接 |
| 行首缩进 | 层级 / 分组归属 |
| `(名称)` | 参与者 / 角色 |
| `[名称]` | 判断节点 |
| `#` 开头 | 注释，不参与解析 |

每种图在此基础上加自己的少量方言（例：类图用 `class X { }` 包裹成员，用例图用
`-include->` / `-extend->`，ER 图用 `1--N` 表示基数）。

**判定点：`DiagramDslService` 支持的 type 枚举** —— R1「只改 8 种」由它唯一决定，
TABLE3 传入时直接拒绝并给出「三线表请使用三线表页面」的提示，而不是静默走通用逻辑。

## 3. User Stories

1. 作为写毕业论文的学生，我打开系统图页想画时序图，希望直接敲几行
   `用户 -> 系统: 登录请求` 就能出图，而不是先建参与者、再建消息、再选类型。
2. 作为用户，我写的 DSL 有语法错误时，希望系统告诉我**第几行、哪个片段不认识**，
   并给我一个该图的可运行示例，而不是什么都画不出来。
3. 作为用户，我此前用表单保存过的图，再次打开时希望还能正常编辑（不被新交互抛弃）。
4. 作为用户，我在画布上直接拖动/改名之后，希望切回文本视图时这些改动还在，
   不会被文本覆盖回旧版本。
5. 作为不熟悉语法的用户，我希望每种图都有一个「填入示例」按钮，点了就能看到
   这种图长什么样、语法怎么写。
6. 作为用户，当 DSL 怎么都写不对时，我希望还能展开原来的表单手工填完，不被卡死。

## 4. Implementation Decisions

1. **解析权威在后端。** 新增 Service 承担 `parse(type, text)` 与 `render(type, config)` 两个方向。
   前端不实现第二份语法，避免两端语义漂移。
2. **`render` 不是可选品，是 R4 的载体。** 没有它，用户在画布/表单上的改动切回文本就会丢。
   往返一致性由测试锁定：`parse(render(c))` 与 `c` 在结构属性上等价。
3. **DSL 文本需要持久化。** 已保存的图只存了结构化配置，若不同步存 DSL 原文，
   下次打开无法回填输入框。故保存链路要一并存文本；老数据没有文本时走第 5 条降级。
4. **错误必须结构化。** `parse` 的失败结果携带：行号、无法识别的片段、该图的语法提示。
   **判定点唯一在 `parse`**，前端只负责渲染这三个字段。
5. **存量数据降级策略：** 打开老图时若 DSL 文本缺失，用 `render(config)` 反向生成回填；
   `render` 也失败（配置残缺）时，文本框留空但表单照常可用，绝不阻断用户编辑。
6. **表单是降级通道，不是历史包袱。** DSL 解析失败或用户不愿写文本时，展开表单仍可完成
   全部配置，生成链路与今天完全一致（RuleEngine 不动）。
7. **预览走防抖。** 文本变更后延迟数百毫秒再请求解析，避免逐字符打接口。
8. **导出与渲染不动。** X6 画布、Dagre 布局、SVG / PNG / Mermaid 导出行为保持现状。

### 规则 → 唯一判定点对照

| 规则 | 谁来判断（唯一） |
| --- | --- |
| R1 只改 8 种 | `DiagramDslService` 的 type 枚举 |
| R2 文本为主入口 | 前端视图默认态（文本视图优先） |
| R3 本地解析 | Service 不注入任何外部客户端 |
| R4 双向不丢 | `render` + 往返测试 |
| R5 存量兼容 | 加载流程：`render(config)` 回填 + 失败留空不阻断 |
| R6 字段不删、默认折叠 | 前端视图（纯展示层） |
| R7 错误可定位 | `parse` 返回结构化错误 |
| R8 每图一个示例 | 前端内置示例表（每图一条） |
| R9 导出不变 | 不动 X6 / 布局 / 导出 |
| R10 画布可编辑 | 前端 X6 交互配置 |

## 5. Testing Decisions

**接缝（唯一）：后端 Service 层，JUnit。** 理由：复用现有测试设施（仓库已有 30 个 JUnit 测试），
前端目前没有任何测试基础设施（无 vitest / jest / test 目录），一个接缝即可覆盖 8 种图的正反双向。

从该接缝观察三类断言：

1. **正向解析**：给定 DSL 文本 → 断言产出的 Config 结构（参与者数、消息序列、类成员、关系类型等）。
2. **错误定位**：给定含语法错误的文本 → 断言返回的行号与无法识别的片段与预期一致。
3. **往返一致**：`parse(render(c))` 与 `c` 结构等价（覆盖 8 种图各自的 Config）。

**不做**：本轮不为前端引入测试框架（成本大于收益）；浏览器端到端仅作人工冒烟，不作为 Gate 依据。

## 6. Out of Scope

- 三线表（TABLE3）的任何改动
- `/table3`、`/er` 独立页与系统图内 tab 的重复入口合并（本轮只澄清，不处理）
- 引入大模型 / 任何外部 API（R3）
- 改造 X6 渲染、Dagre 布局算法、SVG / PNG / Mermaid 导出
- 修改 6 个 RuleEngine 产出的图模型结构（只在其上新增解析层）
- DSL 的语法高亮、自动补全、错误波浪线（可二期）
- 移动端适配、协同编辑、版本历史

## 7. Further Notes

- 8 种图的方言清单需在实现时逐图定稿，每种图的示例文本要取自真实论文场景
  （如「学生提交论文 → 教师审核 → 归档」），不要用 `foo/bar` 这类无意义占位。
- 若将来接入大模型，DSL 可作为「模型输出的目标格式」—— 模型只需产出 DSL 文本，
  复用本轮解析层即可成图，无需改渲染链路。这是选 DSL 而非直接调模型的附带收益。
- 风险：8 种图逐一实现方言，工作量集中。建议按 Plan 站拆分时，先做 1 种图打通全链路
  （解析 → 生成 → 画布 → 反向回填），再横向复制到其余 7 种，避免 8 份半成品。
