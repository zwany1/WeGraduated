## 三、通过项（重点结论）

### 3.1 特殊字符零丢失

`e5` 的 15 项字符逐项校验全部保留：

```
&                        OK        emoji 🎓                 OK
<                        OK        emoji 📚                 OK
>                        OK        日文 日本語               OK
"                        OK        俄文 Русский             OK
'                        OK        阿拉伯 العربية           OK
数学 ± × ÷ ≈ ≤ ≥          OK        全角 ，。；：！？          OK
破折号 ——                 OK        300 字符无空格串           OK
200 字符超长 URL          OK
```

说明 XML 写入侧做了正确的转义（`&amp;` / `&lt;` 等），emoji 与阿拉伯语也没有被字体替换吞掉 —— 这是最容易出问题的地方，表现良好。

### 3.2 超长内容不截断

- 超长标题 180 字 × 3 段：完整保留，标题样式正确（黑体 14pt / 12pt）
- 超长单段 20000 字符：字符数完全一致，仍按正文格式（宋体 12pt / 首行缩进 2 字符 / 20 磅固定行距）
- 360 段文档：10 章 50 节全部识别并套用对应标题格式，渲染耗时约 1 分钟（4 个任务并发）

### 3.3 幂等性通过

同一文档用同一模板连续排版两次，逐段比对文本 + 样式 + 字号 + 字体 + 对齐 + 行距 + 缩进：

```
段落数 A=13  B=13
差异段落数: 0
```

### 3.4 正常文档格式全部正确

`e1` 产物逐项核对：

| 元素 | 实测 |
| --- | --- |
| 一级标题 | `Heading1` 黑体 28 half-pt（14pt） |
| 二级标题 | `Heading2` 黑体 24（12pt） |
| 三级标题 | `Heading3` 楷体 24（12pt） |
| 正文 | 宋体 24（12pt） |
| 图题注 | 宋体 21（10.5pt 五号） |
| 参考文献条目 | 宋体 21 + 自动编号 `[1]` |

## 四、发现的问题

### 🔴 P1：0 字节文件会打断整批提交，且产生孤儿文件

**现象**：同时选中「1 个正常文件 + 1 个 0 字节文件」点「批量排版」，界面弹一次 `文件不能为空` 后**就没有下文**：正常文件不会被提交，但它的二进制**已经上传到服务器**（数据库里有记录，却没有对应排版任务）。

**复现步骤**：
1. 登录 → 进入「排版任务」
2. 选择格式方案
3. 一次选中 `e6_empty_paragraphs.docx` 与 `e7_zero_bytes.docx`
4. 点「批量排版」
5. 观察：只弹出一次 `文件不能为空`，任务列表无新增，两个文件仍留在待提交区
6. 查库：`select * from t_paper_file where user_id=18 order by id desc` 可看到正常文件已入库，但 `t_format_task` 无对应任务

**根因**：`FormatTask.vue:548 submit()` 用 `for` 串行 `await uploadPaper(f)`，任一文件抛错即跳出循环，此前已上传成功的 `fileIds` 不会被提交，也没有回滚。

**建议**：逐个文件 try/catch，收集失败清单，把成功的那部分照常提交，最后汇总提示「3 篇成功、1 篇失败（xxx.docx 文件不能为空）」；或在上传前用 `file.size === 0` 前置校验并拦截。

---

### 🔴 P2：空文档 / 无标题文档被判定为「结构识别良好」

**现象**：上传只有 5 个空段落的 `docx`，排版**成功**，预览为空白页，但排版报告显示 `0 章 / 0 节 / 0 图 / 0 表 / 0 文献 / 0 正文段落`，结论却是 **「未发现疑似标题问题，结构识别良好」**。

**复现步骤**：
1. 上传 `e6_empty_paragraphs.docx` → 选模板 → 批量排版
2. 任务显示「已完成」
3. 点该行「报告」
4. 看到 6 个 0 和「结构识别良好」（截图 `19_empty_report.png`）

**影响**：用户（尤其是把文档贴错的学生）会误以为排版成功，实际什么都没排。

**建议**：报告里增加兜底判定 —— `chapterCount === 0 && bodyParagraphs === 0` 时提示「未检测到任何正文内容，请确认文档是否正确」；`chapterCount === 0` 但正文非空时提示「未识别到章节标题，请检查标题是否使用了 Word 标题样式或 1 / 1.1 编号」。

---

### 🟠 P3：伪 `.docx` 上传不拦截，失败信息重复且暴露内部类名

**现象**：把 `.txt` 改名为 `.docx` 上传，**上传接口返回成功**（`t_paper_file` 有记录，415 字节）；直到排版阶段才失败，失败原因为：

```
排版失败：排版失败：处理文档时发生错误（ZipException: Unexpected record signature: 0xe499bfe8）
```

**复现步骤**：
1. 把任意文本文件改名为 `e8_fake_text.docx`
2. 上传 → 界面无任何异常，文件正常入列表
3. 点「批量排版」→ 任务失败
4. 点「查看原因」→ 看到上述文案

**问题点**：
- 上传阶段未校验文件魔数（`PK\x03\x04`），坏文件要等到占用一次排版任务才暴露
- 错误文案「排版失败：」重复两次
- 直接暴露 `ZipException`、十六进制签名，普通用户无法理解

**建议**：上传时读取前 4 字节校验 ZIP 头；失败文案改为「文件已损坏或不是有效的 .docx，请用 Word 重新另存后再试」。

---

### 🟡 P4：预览里的标题是蓝色，与产物不一致

**现象**：排版结果预览中，「1 绪论」「1.1 研究背景」「1.1.1 国内外现状」全部渲染为**蓝色**；但产物 `document.xml` 里 `heading 1/2/3` 样式的 `w:color` 均为 `000000`，正文 run 无任何 `color`。

**复现步骤**：
1. 排版 `e1_normal.docx`
2. 点「预览」，打开「排版结果预览」（截图 `06_preview_dialog.png`）
3. 观察标题为蓝色
4. 下载产物用 Word 打开 → 标题是黑色

**影响**：用户会以为排版把标题染色了，反复回去改模板。

**建议**：`DocxCompare` / docx-preview 渲染时显式覆盖 heading 颜色为继承值或 `#000`。

---

### 🟡 P5：四 / 五级标题回落为正文格式，层级不可辨

**现象**：模板只配置了 heading1~3。`e10` 中 Heading4 / Heading5 段落被套成 **宋体 12pt**，与正文完全同字号同字体，视觉上无法区分层级。

```
Heading1  sz=28  黑体   1 一级标题
Heading3  sz=24  楷体   1.1.1 跳过二级直接三级
Heading4  sz=24  宋体   1.1.1.1 四级标题     ← 与正文同
Heading5  sz=24  宋体   1.1.1.1.1 五级标题   ← 与正文同
```

**建议**：`RuleSet.rule()` 对缺失的 headingN 规则，改为继承最近的已配置上级规则（或在预设里补 heading4/5：黑体/楷体小四，加粗以区分）。

---

### 🟢 P6：孤立的表题注不套用题注格式

**现象**：`e1` 里「表2-1 硬件清单」后面没有紧跟表格（只是普通段落），产物中该段为 `sz=24 宋体`（正文格式），而同文档的「图2-1 系统总体结构图」被正确套成 `sz=21 宋体`。

**说明**：题注识别依赖「紧邻表格/图片」的上下文，孤立题注被当正文。严格说这是合理设计，但用户把题注写在表格上方隔一行时就会失效，建议文档里说明该约束，或在报告里提示「疑似题注但未紧邻图表」。

## 六、结论

- 引擎对**内容层面**的鲁棒性很好：超长标题、20000 字单段、360 段、特殊字符/emoji/多语言全部无损，格式套用准确，重复排版结果完全一致。
- 问题集中在**入口校验**与**反馈质量**：坏文件（0 字节 / 伪造 docx）没有在入口拦住，且会污染批次；空文档给出「结构识别良好」的误导性结论；预览颜色与产物不一致。
- 按修复优先级：**P2（误导性报告）> P1（批次中断 + 孤儿文件）> P3（入口校验 + 报错文案）> P4（预览色差）> P5 / P6**。
